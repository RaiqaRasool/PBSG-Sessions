# Live Session Script: MCP in Real Work

## Opening

Ask the room:

> What is one task where your AI assistant gives a reasonable answer but still cannot finish the job?

Take two or three examples. Listen for missing access: a repository, current documentation, a browser, a website, or a local file.

Then frame the session:

> A model can reason and write, but useful work often depends on context and tools. MCP gives the assistant a standard way to connect to them. Today we will judge those connections by outcomes, not by how many servers we can install.

Show the pattern:

```text
Goal → prompt → MCP connection → verifiable result
```

## 1. GitHub: From issue to implementation plan

Open [1.GithubMCPSetup.md](1.GithubMCPSetup.md).

Start with the read-only prompts. Ask attendees what they would normally do after receiving an unfamiliar issue: open the issue, search the repository, identify likely files, and form a plan.

Run the final prompt and compare its result with that manual sequence.

Key point:

> The useful capability is not “reading GitHub.” It is connecting external project context with local code while keeping the first pass read-only.

## 2. Context7: Replace plausible memory with current docs

Open [2.Context7Setup.md](2.Context7Setup.md).

Ask:

> Who has copied an answer that was correct for an older version of a library?

Use the SQLAlchemy prompt. Point out the request for the documentation source as well as the code pattern.

Key point:

> The model still reasons, but the answer is grounded in current, library-specific documentation instead of memory or a broad web search.

## 3. Playwright: Let the audience watch the work

Open [3.PlayWright.md](3.PlayWright.md).

This is the most visual demonstration. Before running the full task-list prompt, ask the audience to predict which step is most likely to fail.

Run the workflow and keep the final step-by-step report visible. Return to the predictions when the test finishes.

Key point:

> A strong agent task contains actions and observable checks. “Test my app” is vague; this prompt defines what success looks like.

## 4. Firecrawl: Turn a page into a result

Open [4.Firecrawl.md](4.Firecrawl.md).

Show the events page first so the audience sees the noisy source. Then run the extraction prompt.

Ask:

> Which part makes this output reusable—the scrape, or the constraints on the result?

Key point:

> Access to the web is only half the workflow. A bounded schema turns page content into information another person or system can use.

## 5. MarkItDown: Bring your own difficult file

Open [5.MarkItDown.md](5.MarkItDown.md).

Ask attendees which format causes them the most friction: PDF, PowerPoint, Word, Excel, audio, or video. Choose one of the prepared examples, convert it, and ask a question about the resulting content.

Key point:

> Conversion is not the final outcome. It makes previously awkward content available for summarization, comparison, extraction, and follow-up questions.

## Optional: Presentation workflows

If the room is interested in content creation, show [7.ExistingPlugins](7.ExistingPlugins) as a short example of using an already available capability. Keep [6.PowerPoint.md](6.PowerPoint.md) as a resource for later exploration rather than a core demonstration.

## Closing

Return to the examples shared at the beginning and ask:

> What information or action was your assistant missing, and what guardrail would you add before connecting it?

Close with three ideas:

1. Start with a real job, not a server directory.
2. Make success observable in the prompt.
3. Begin read-only and expand permissions deliberately.

Invite attendees to choose one handout and adapt its prompt to a task they already do.
