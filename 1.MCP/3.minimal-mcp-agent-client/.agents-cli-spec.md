# Transparent MCP Agent Spec

## Overview

Build a minimal local command-line agent that makes the boundary between model decisions and MCP client behavior visible. The agent accepts one user question, discovers the existing Phoenix MCP server's resources, lets a local model served by LM Studio decide whether to read an advertised resource, performs that MCP operation, returns the result to the model, and prints the final answer.

The implementation must log each meaningful boundary without presenting private model reasoning: user input, MCP discovery results, model request inputs, model tool decisions, MCP client operations, MCP results, and the final answer.

## Example Use Cases

### Read project status

Input:

```text
What is the current status of Project Phoenix?
```

Expected flow:

1. The agent exposes the Phoenix resource-reading capability to the model.
2. The model requests the Phoenix status resource.
3. The MCP client reads `project://phoenix/status` from the existing stdio server.
4. The agent supplies the resource contents to the model.
5. The model answers the user's question.

### Answer without MCP

Input:

```text
What is 2 + 2?
```

Expected flow:

1. The model does not request the Phoenix resource.
2. No MCP read occurs.
3. The model answers directly.

## Tools Required

- LM Studio's OpenAI-compatible Responses API: produce model decisions and the final response through a locally served model.
- OpenAI Python client: communicate with LM Studio by using its configurable OpenAI-compatible base URL.
- MCP Python SDK client: start and communicate with the existing Phoenix FastMCP server over stdio.
- Existing Phoenix server: bind-mounted from `/Users/rasool/Desktop/MCP/minimal-mcp-teaching-server` and launched directly as the agent container's stdio child.

## Constraints & Safety Rules

- Run locally as a command-line prototype.
- Keep the implementation framework-free; do not use ADK or another agent framework.
- Expose every tool advertised by the connected MCP server, including
  `add_project_update`.
- Use Docker and Docker Compose so Python dependencies remain isolated from the host.
- Do not add Streamable HTTP, a web UI, deployment, memory, multi-agent orchestration, or a database.
- Never print secrets or the API key.
- Do not claim to expose hidden chain-of-thought. Log only observable API inputs, outputs, decisions, and MCP operations.
- Keep MCP protocol stdout separate from diagnostics when launching the stdio server.

## Success Criteria

- A single CLI command accepts a user question.
- The trace clearly distinguishes the model, agent loop, MCP client, and MCP server boundaries.
- A Phoenix status question causes exactly one read of `project://phoenix/status`.
- An unrelated question can complete without an MCP read.
- Discovered MCP tools are available to the model through dynamic function
  definitions.
- Focused deterministic tests cover translation and routing logic without asserting on nondeterministic model prose.
